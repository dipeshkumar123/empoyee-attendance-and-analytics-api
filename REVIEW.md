# REVIEW.md

List every defect you found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `department_trend_pipeline` (lines 697-717) | Uses MongoDB's `$round` operator which implements banker's rounding (round half to even), but R8 requires half-up rounding for `attendance_rate` (4 decimals) and `moving_avg_7d` (4 decimals). | Compare trend output for a department where `present_count / headcount` yields a value like 0.12345 - banker's rounding would give 0.1234, half-up should give 0.1235. | Replace `$round` in the aggregation with a `$addFields` stage that computes rounding using half-up logic via `$let` and arithmetic, or compute rounding in Python after fetching results (but spec requires aggregation). Since MongoDB lacks native half-up, compute in Python post-aggregation for these two fields. |
| 2 | `dt_to_ms` (line 110-115) | Uses `round(dt.timestamp() * 1000)` which can introduce rounding errors when converting UTC datetime to epoch milliseconds. Since all stored datetimes are already truncated to whole seconds (microsecond=0), `int(dt.timestamp() * 1000)` is exact and safer. | A datetime like `2026-07-06 03:58:00+00:00` might convert to `1783310280000.0000001` and round to `1783310280000` correctly, but edge cases near float precision boundaries could flip. | Change to `int(dt.timestamp() * 1000)` since `dt` always has `microsecond=0`. |
| 3 | `round_half_up` (line 182-185) | Uses `Decimal(str(value))` to avoid binary floating-point representation issues, but `str(float)` can still produce unexpected strings (e.g., `str(1.005)` → `'1.005'` but `str(2.675)` → `'2.675'` - both round correctly with half-up, yet `str(0.1+0.2)` → `'0.30000000000000004'` would quantize incorrectly). | Aggregation sums like `present_days` (sum of 0.5 and 1.0) are exact in decimal, but MongoDB returns doubles that may have tiny binary artifacts (e.g., `1.9999999999999998` instead of `2.0`). | Use `Decimal(value).quantize(...)` directly for floats that are already Decimal-computed, or for aggregation results use `Decimal(str(round(value, 10)))` to normalize first. |
| 4 | `employee_monthly` (line 1024) | Rounds `present_days` with `round_half_up(present, 2)` but `present` comes from MongoDB `$sum` of doubles. Floating-point sum of 0.5 increments can yield `1.9999999999999998` which rounds to `2.00` correctly with half-up, but `2.0000000000000004` would also round to `2.00`. Generally safe but worth noting. | Monthly summary for an employee with two half-days shows `present_days: 1.0` instead of `1.00` (formatting) or edge case with many records. | Current implementation is acceptable; the quantization handles it. No fix strictly needed. |
| 5 | `regularize_attendance` snapshot (lines 972-978) | Optimistic concurrency snapshot includes `emp_code`, `date`, `status`, `punch_in`, `punch_out` but not `work_hours`, `late_minutes`, `overtime_minutes`, `half_day`. If another process somehow modified only derived fields (not possible in this API since only this endpoint modifies records), the conflict would not be detected. | Not observable in normal operation since only `regularize_attendance` modifies records and always recomputes derived fields from punch times. | Acceptable as-is; the snapshot covers all fields that a client can directly modify. |
| 6 | `attendance_list_sort` (line 510-511) | Returns a dict `{"date": DESCENDING, "emp_code": ASCENDING}` and endpoint calls `.items()` on it. In Python <3.7 dict order wasn't guaranteed, but Python 3.11+ preserves insertion order. The dict is constructed with date first, so sort order is correct. | Only a concern if run on Python <3.7. | Use list of tuples `[("date", DESCENDING), ("emp_code", ASCENDING)]` for explicit ordering guarantee. |
